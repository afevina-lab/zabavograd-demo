# Правила проекта «Забавоград» · единый публичный репозиторий

**Единственный исходник:** `afevina-lab/zabavograd-demo/main`; `gh-pages` — собранная публикация. Старый приватный `afevina-lab/zabavograd` не является источником для дальнейшей разработки и служит временной страховочной копией.

Перед изменениями читать актуальные правила README.md и AGENTS.md, затем выбирать профильный документ и необходимые разделы через `outputs/README.md`. Не загружать все большие журналы целиком: искать нужное решение и читать его контекст. Для новых продуктовых требований — PROJECT.md, для утверждённых уточнений — DECISIONS.md, для игр — GAMES.md, для библиотеки — LIBRARY_EDITOR.md, для изображений — ASSETS.md, для оформления — VISUAL_SYSTEM.md. Поздние подтверждённые решения приоритетнее исторических. Отвечать пользователю по-русски, конкретно.

- Только `outputs/library-modules/` — редактируемый источник словарных данных. `editorial/library-source-mode.json` фиксирует канонический режим; старый монолит не восстанавливать рядом. `library.json`, `semantic-graph.json`, `public/grammar-frames.json`, HTML и SQLite — производные. Изменения — точные пакеты по ID, preview и проверенный кандидат.
- ID, значения, категории, веса, формы, фонетика, двусторонние связи, семьи животных и привязки изображений должны сохраняться при миграции. Разные слова/значения с одинаковым написанием не склеивать без проверки.
- Отделять статус `suggested` от `verified`; 55 неутверждённых моделей действия не передавать генератору. Внешние лингвистические источники использовать для проверки, с учётом лицензий; во время игры всё статично и офлайн.
- Не придумывать связи слов, утверждённость фонетического разбора или грамматические формы. Не создавать автоматические ссылки для спорных рисунков. На Git только сжатый WebP; исходные PNG сохраняются локально.
- Не публиковать данные детей, личные пути к исходникам, ключи или сторонние материалы без прав на публикацию.
- Списание жизней выбирает педагог: вручную (кнопка, сердца, F8), за ошибку или оба способа; есть отмена последнего списания. По умолчанию вручную. Завершение игры не является доказательством освоения навыка.
- UI темы только в `src/design-system/themes.ts`, анимации — в `motion.ts` и `motion.css`. Не дописывать специальные темы прямо в компонентах.
- Проверки перед публикацией — по утверждённому [CI_POLICY.md](docs/CI_POLICY.md): DOCS / LIBRARY / GAME / THEME / FULL. Не запускать полный браузерный набор на каждую локальную правку; обязательные статические, словарные и unit-проверки для изменений runtime сохраняются. Неизвестный или смешанный diff — FULL; ручной FULL доступен. Публикуется именно проверенная сборка.
- Публикация считается завершённой только после успешного GitHub Actions и проверки файла в `gh-pages`. Не считать Pull Request или запись в `main` публикацией сайта.

- Правки runtime по запросу пользователя доводить до GitHub и проверенной публикации сайта; не останавливаться на локальном результате, если пользователь прямо не попросил обратное. Чисто документальные изменения не требуют повторной публикации; сверить существующий релиз.

- При точечной работе со словарём сначала использовать `npm run library:tool -- find|inspect|select|gaps|inventory` (см. `docs/LIBRARY_TOOLKIT.md`), а не читать весь V2 в контекст. Изменять поддерживаемые поля пакетами с ожидаемыми прежними значениями; предварительно выполнить dry-run. Сохранять статус проверки, обязательные валидаторы и единственный источник. Не использовать инструмент для смены ID или автоматического утверждения предложений.
- Для GitHub-коннектора без shell использовать производный индекс `library-index` (сначала сверить SHA мастера), а для точечных чтений и патчей — протокол `docs/LIBRARY_REMOTE.md`. Публикация кандидата в отдельной ветке не означает утверждение или выпуск. Не редактировать служебные индексы вручную.

- После завершённой одноразовой миграции или импорта удалять использованный скрипт и временный код из активной ветки после проверки зависимостей и результата. Не переносить их в папку архивного кода: Git сохраняет предыдущие версии. Достаточен краткий журнал с датой, назначением, результатом и ссылкой на коммит. Повторно используемые инструменты, тесты, действующие CI-процессы и уникальные редакторские данные сохранять. Не удалять активную ветку визуальной разработки или её проверочные средства без подтверждения завершения переноса.
