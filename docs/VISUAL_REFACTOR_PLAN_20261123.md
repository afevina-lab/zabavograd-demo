# План рефакторинга визуальной архитектуры «Забавограда» — без редизайна

**Дата:** 23.11.2026  
**Статус:** планирование; реализация не начата. **Приоритет №1: оптимизация CI/CD до визуального рефакторинга.**  
**Источник:** публичный репозиторий `afevina-lab/zabavograd-demo`, исходная ветка `main`.  
**Область изменений на данный момент:** только этот документ в отдельной ветке планирования. Исходники, ассеты, `main` и `gh-pages` не изменять до отдельного решения о начале реализации.

## 1. Цель и жёсткие ограничения

Переписать организацию кода, отвечающего за визуал, **не меняя существенно утверждённый внешний вид**. Вместо накопления CSS-исключений создать простую композиционную систему: единая геометрия, единые компоненты, три темы как наборы визуальных токенов и ассетов, игровые сцены как отдельные композиции.

**Не делать редизайн.** Сохранить утверждённые WebP/PNG-ресурсы и прозрачность, акварельные фактуры, размеры и пропорции, узнаваемое оформление кнопок и окон, эффекты карточек, фоновые сцены, анимации, расположение элементов по согласованным макетам. Допускаются только отдельно согласованные исправления *известных дефектов*, не случайные изменения при переписывании.

**Не затрагивать:** игровую математику и правила, библиотеку слов и её ID, фонетику и семантические связи, подбор материалов, сохранённые педагогические наборы, систему публикации данных. Взаимодействия (включая выбор слов, перетаскивание, сохранение, паузу, результат, клавиатуру и touch) должны оставаться работоспособными.

**Не менять технологический стек ради самого рефакторинга.** React, TypeScript и Vite подходят; новый игровой движок или готовая чужая дизайн-система не требуются.

## 3. Целевая архитектура

### 3.1. Разделение ответственности

1. **Tokens:** геометрия (система шагов 4/8/12/16/24/32 px с задокументированными вариантами), типографика, размер контролов, слои `z-index`, допустимые состояния и адаптивные параметры. Никаких игровых названий и тем.
2. **Themes:** палитры, фактуры, WebP, наборы UI-скинов, фоновые ресурсы. Сохранять центральный реестр `themes.ts`. Темы не влияют на игровую логику и основную раскладку.
3. **Primitives:** Button, IconButton, Panel, Select, Slider/RangeSlider, Checkbox, Radio, Switch, Tabs/Chip, Disclosure, Card, Tooltip. Каждый владеет собственным оформлением и состояниями; варианты задаются явными props / `data-variant`.
4. **Compositions:** SettingsWindow, SetupPreview, GameToolbar, GameViewport, GameDialog/ResultDialog, выбор материала. Составляют компоненты, но не переопределяют их внутреннее оформление.
5. **Game layouts:** собственная композиция «Мемори», «Сортировки», «Соотнесения», «Конвейера», «Превращений». Игровые правила отдельно от CSS.
6. **Motion/scenery:** единые временные константы и базовые анимации; отдельная конфигурация фоновых слоёв. Специфические движения игровой механики допускаются в её модуле, но не создают новое оформление базовых контролов.

**Один параметр — один владелец.** Например: высота кнопки живёт у кнопки, межсекционный интервал — у композиции настроек, рисунок рамки — у темы. Компонент не должен зависеть от порядка подключения несвязанных CSS-файлов.

### 3.2. Предлагаемая структура (проектная, не создавать пока)

- `src/ui/tokens/` — геометрия, типографика, тема/материалы, общие слои.
- `src/ui/primitives/{Button,Select,Slider,...}/` — компактные React-компоненты и локальные стили (рассмотреть CSS Modules).
- `src/ui/compositions/{SettingsWindow,GameToolbar,GameDialog,...}/` — общие композиции.
- `src/ui/scenes/` — тематические слои и художественные элементы.
- `src/ui/motion/` — общие анимации и длительности.
- `src/games/<game>/` — исключительно специфические раскладки и эффекты механики, без альтернативных версий общих элементов.

Имена/папки предварительные. Сначала утвердить интерфейсы компонентов, потом переносить файлы. CSS Modules и/или `@layer` использовать только после проверки, что при переносе не меняется каскад (особенно порядок `!important`). Не смешивать глобальные и локальные селекторы без явных правил.

### 3.3. Контракт компонентов

- `SettingsWindow` принимает **явные слоты**: материал, задание, правила, дополнительные параметры, оформление, предпросмотр и действие запуска. Размещение колонок/панели темы/фиксированного футера принадлежит композиции. Никакого анализа DOM-потомков и имени игры; специфику расположения передавать документированным режимом/слотами.
- `GameToolbar` принимает явные `actions`, `status`, `task` и `fullscreen`; не распознаёт кнопки по тексту.
- `GameSelect`/`SelectControl` получают явно заданный icon (или семантический тип), не подбирают по русской подписи.
- Контролы задают явные состояния: default, hover, focus-visible, pressed, selected, disabled, error. Специальная геометрия — только как именованный вариант с обоснованием.
- Диалоги/поповеры используют единое позиционирование, top layer/overflow/z-index контракт; не размещаются через случайные смещения относительно игровой сцены.
- Композиция может управлять внешним размером и местом компонента, но не его внутренними `padding`, рамками, иконками и скином.
- Внутри разных игр общие компоненты **не** переопределяются селекторами вида `.game-name .shared-component`.

### 3.4. Особенности художественного оформления

Сохранить оригинальные утверждённые ресурсы и их правила применения:

- Игровые карточки, где требуется цельное изображение 1:1, отображать **цельным WebP** без швов/деформации.
- Для согласованных масштабируемых рамок, панелей и шапок использовать подходящий **9-slice** и сохранять толщину рамок; не переносить 9-slice автоматически на карточки.
- Отдельно описать лицевую/оборотную стороны, поверхности сортировки, конвейера, соотнесения и нейтральной темы превращений.
- Анимации должны работать с цельным визуальным объектом, не анимировать независимо сегменты рамки.
- Не менять палитры, насыщенность, прозрачные углы, иконки, декоративные слои и approved WebP «ради унификации».

## 4. Последовательность работ и критерии окончания

### ПРИОРИТЕТ №1 — этап −1. Ускорение проверок и публикации (CI/CD) **первым делом**

**Обязательное первое действие при разрешении начать реализацию — до переписывания CSS, компонентов и игровых экранов.** Не путать со стадией 0: сначала устраняем избыточные повторные прогоны CI/CD, затем фиксируем визуальный baseline на этапе 0 и начинаем UI-рефакторинг.

**Проблема:** даже маленькая правка запускает обширный набор браузерных сценариев (пять игр, три темы, пять размеров, несколько состояний и окон), а часть архитектурных проверок вызывается повторно через `npm test`/`npm run build`. Обычная публикация не должна требовать условно «200 проверок на час»; реальные длительности и повторения сначала измерить по GitHub Actions, не принимать оценку за метрику.

#### Требуемые режимы

| Режим | Условие запуска | Набор |
| --- | --- | --- |
| **FAST — обязательный минимум** | Любой обычный коммит/PR и небольшая публикация | Корректная сборка, TypeScript, основные инварианты архитектуры/целостности, smoke выбранной страницы или критического сценария, контроль ошибок и отсутствующих ресурсов. Базовые гарантии не отключать. |
| **TARGETED — выборочные проверки** | Изменена конкретная игра, компонент, CSS-область, библиотечный ресурс или связанные файлы | Зависимые тесты/сцены/темы/размеры; общий компонент — все затронутые потребители, а не только игра, в которой замечена проблема. |
| **FULL — полный набор** | Крупный общий рефакторинг, изменение инфраструктуры публикации/контрактов, высокий риск, ручной запрос, перед значительным релизом | Все игры, темы, размеры, основные диалоги и действия, расширенные регрессии и сравнение снимков. Опционально — еженедельный плановый прогон, не блокирующий мелкие изменения задним числом. |

**Классификация по затронутым путям и зависимостям:** документация → минимум; одиночный медиафайл → проверка файла, ссылок, сборки и представления; локальная механика → её тесты + smoke; общий контрол → все зависимые места; изменение общих layout/theme/motion токенов, схемы библиотеки, публикации или неизвестный тип файла → расширенный набор, при высокой неопределённости FULL. Порог по числу строк не годится: изменение одной глобальной CSS-переменной может затронуть все игры.

#### Конкретные задачи

- [ ] Измерить по последним workflow-запускам: время шагов, число повторных проверок, число действительно выполняемых сценариев, cache hit/miss, время сборки/публикации, частоту ложных падений. Сохранить измерения «до».
- [ ] Устранить дубли: `check:architecture` сейчас вызывается отдельно, из `npm test` и из `npm run build`. Сформировать один ясный граф зависимостей команд с однократным выполнением общих проверок в CI.
- [ ] Разделить **проверку PR/коммита**, **сборку релизного артефакта** и **деплой**. Публикация не должна повторять длинные тесты, результаты которых относятся к тому же SHA и артефакту; нельзя деплоить непроверенный артефакт.
- [ ] Настроить определение изменённых путей + карту зависимостей и безопасный fallback на FULL/расширенный набор при неизвестной области изменений.
- [ ] Организовать FAST/TARGETED/FULL в workflow с явным `workflow_dispatch`-выбором режима и автоматически рассчитанным режимом по умолчанию. Автоматическую эскалацию для рискованных изменений нельзя обойти случайным ручным выбором FAST.
- [ ] Параллелить независимые браузерные задачи (matrix по играм/темам или наборам), ограничивая параллелизм разумно; убрать три последовательных прогона там, где они независимы.
- [ ] Использовать `actions/cache` / `setup-node` cache, повторное использование сборки и артефактов, а также корректную отмену устаревших PR-проверок без потери актуальной публикации.
- [ ] Добавить проверку **именно опубликованной версии** (SHA/ресурсы/главный маршрут), но сделать её быстрой; тяжёлую визуальную регрессию не запускать повторно без необходимости.
- [ ] Настроить расписание полного прогона только если оно действительно полезно; не допускать, чтобы плановый FULL автоматически перезаписывал выпуск или тормозил обычные коммиты.
- [ ] Вывести в отчёт причину выбранного режима, фактически выполненные тесты, длительность, ошибки, пропущенные группы и ссылку на артефакты.
- [ ] Проверить, что документационные и малорисковые изменения не запускают полный браузерный обход, а критические изменения нельзя выпустить без соответствующих проверок.
- [ ] Зафиксировать замеры «после» отдельно для примеров: документация, один WebP, локальная игра, общий компонент, глобальная визуальная архитектура.
- [ ] Обновить документацию и контроль workflow, исключить альтернативные способы публиковать `gh-pages` без gate.

**Критерий готовности:** обычные изменения проходят FAST или TARGETED, тяжёлый FULL выполняется по реальному риску/запросу, нет повторяющихся одинаковых тестов и обязательного полного браузерного обхода для каждой мелочи. Сокращение времени подтверждено измерениями в Actions; базовая безопасность публикации не ухудшилась.

**Особое условие:** сначала менять только CI/CD в контролируемой рабочей ветке, отдельно протестировать маршрутизацию проверок. До утверждения результатов не переключать действующий процесс публикации. Затем продолжить с этапа 0 по визуальному плану.

## 5. Правила исполнения

1. **Не переписывать всё одним огромным коммитом.** Вести рефакторинг в отдельной ветке с небольшими проверяемыми изменениями и остановками на каждом этапе.
2. **Никаких правок `gh-pages` вручную.** Публикация возможна только штатным workflow после проверок и утверждения.
3. **Нельзя лечить один экран случайным глобальным override.** Исправить владельца свойства; если нужен вариант, описать его явно.
4. **Не привязывать логику к русскому названию игры, тексту или CSS-классам потомков.** Использовать явные props/слоты/семантику.
5. **Разрешённая визуальная разница:** только предварительно согласованные дефекты и необходимые технические изменения без существенной смены вида. Любая другая разница должна быть устранена.
6. **Не менять игровые данные и механики.** UI-рефакторинг не должен менять поведение упражнений, связи или материал.
7. **Не считать тесты выполненными без запуска.** Для каждого этапа писать: что изменено, какие команды фактически запущены, результаты, снимки и расхождения.
8. **Не удалять старый код заранее.** Миграция должна быть обратимой до завершения верификации.
