## Порядок действий после готовности визуальной ветки

1. Зафиксировать новый актуальный main, сохранить его SHA и неизменяемый резервный снимок. Сверить изменения библиотеки по ID, не перезаписывать их старым снимком.
2. Перенести только библиотечные изменения, урегулировать конфликт потребителей, заново запустить инвентаризацию и тесты.
3. Сгенерировать модули из актуального V2; проверить точную логическую эквивалентность, архив, реестр медиа и идентичность игровых JSON. Не создавать второй редактируемый источник.
4. В одном проверенном изменении добавить outputs/library-modules и маркер editorial/library-source-mode.json, удалить outputs/library-v2.json, обновить AGENTS и все активные читатели/писатели и процессы CI. Старый файл восстанавливается из Git, не хранится параллельно как редакторский.
5. Провести полную проверку игр, всех тем и размеров единожды на границе миграции. Отдельно проверить OAuth/клиент редактора, импорт и экспорт, публикацию и откат. Для обычных последующих словарных изменений использовать целевые проверки; не пропускать проверки ассетов, ссылок, архивных данных и генерации.
6. Только после разрешения на переключение — принять PR и проверить реальный релиз. При сбое откатить согласованный набор изменений целиком, не смешивать модули старого и нового поколения. Если после переключения уже приняты новые словарные данные, сначала сохранить их точный снимок и согласовать обратную миграцию, не терять правки.

До этого момента маркер отсутствует, монолит остаётся текущим каноническим источником. Репетиция проверяет отдельный временный checkout, не является готовностью к публикации.

## 26.11 — режимы проверки интеграции

Репетиция удаления монолита успешно пройдена (45790738206). В `editorial/legacy-library-writers.json` перечислены 17 подтверждённых исторических писателей V2; они блокируются общим guard в модульном режиме до чтения/записи. Это не все возможные динамические зависимости и не адаптация импорта. В режиме legacy старые операции оставлены неизменными. CI проверяет каждый guard после временного переключения.

В интеграционной ветке `library-ci-plan.cjs` выбирает docs (только перечисленные документы), client (только изолированный браузерный контроллер/его тест и документы), full (любое иное изменение, неизвестный diff, ручной запуск). При client выполняются синтаксическая проверка и клиентские тесты; при docs — тест классификатора. Full сохраняет всю прежнюю репетицию. Сравнение использует точные before/after, учитывает удаления и обе стороны переименований. Это не изменение visual-publish на main: проектные проверки публикации согласовать после визуальной ветки. Для финального перехода обязательно ручное full. Сокращённые маршруты ещё следует проверить фактическими push.

## Пилот нового импорта

`import_operations` в отдельном запросе preview/candidate поддерживает create_noun (новое русское существительное, точное значение, существующие категории, предложенный вес; фактический вес 0, ветки не включены по умолчанию, анализ pending) и link_webp (точный ID/лемма/значение, предварительно размещённый WebP, SHA-256, явная отметка проверки). Дубли написания с учётом ё/е, уже используемые пути и известные SHA, замена существующих смысловых карточек и вариантов запрещены. Проверяется контейнер WebP и файл, не качество картинки. Строгий валидатор учитывает отдельное число новых ID, проверяет новые связи и архив; replay поддерживает этот пакет. `projectRegistry` формирует только добавление новых смыслов к прежнему реестру, не публикует его. Новые файлы изображений ещё надо доставлять отдельным проверяемым процессом; в данном пилоте они должны существовать в checkout. Не поддерживаются создание новых категорий, омонимов, глаголов, признаков, активация черновиков и замена старых картинок. Тестовая запись и картинка создаются исключительно в CI.
